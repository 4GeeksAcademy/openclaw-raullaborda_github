> Alcance: descubrimiento de API, autenticación y tres skills de consulta (proyectos, trabajo pendiente, progreso). Las tres se implementaron y probaron contra la API real.

## A. Conversación inicial de descubrimiento

- **Petición inicial:** integrar OpenClaw con la API de 4Geeks para consultar la cuenta de estudiante, proyectos, tareas pendientes y progreso; construir cuatro skills obligatorias y al menos dos adicionales; probar cada una; no escribir tokens en código, documentación o registros; explicar el proceso paso a paso.
- **Solución planteada:** usar la API HTTPS de BreatheCode, autenticación mediante `Authorization: Token …`, skills pequeñas de solo lectura y helpers que no impriman respuestas personales ni credenciales. Revisar antes el material oficial; no ejecutar operaciones de escritura como actualizar o entregar tareas sin una solicitud expresa aparte.
- **Información requerida:** token de estudiante o una credencial ya configurada que pueda verificarse; si la API lo exige para filtrar resultados, contexto de academia/cohorte, obtenido de los endpoints oficiales. No hace falta que el usuario copie aquí el token.
- **Documentación y enfoque:** se revisó la referencia de estudiantes publicada en el repositorio oficial 4GeeksAcademy y su copia local `docs/STUDENT_API_CALLS_REFERENCE.es.md`. Identifica la base habitual `https://breathecode.herokuapp.com`, el formato del token y los endpoints que se enumeran más abajo. La página Swagger responde, pero `GET https://breathecode.herokuapp.com/openapi.json` devolvió HTTP 500; por tanto, esquemas completos, scopes y comportamiento de campos no documentados siguen sin confirmarse. Se limitará la implementación a rutas y datos descritos en la referencia y a respuestas observadas en pruebas reales.
- **Cómo obtener el token, según la referencia:** 4Geeks documenta `POST /v1/auth/login` como login público que entrega el token, pero el documento consultado no especifica su esquema de petición ni los pasos de interfaz para extraerlo. Usa el proceso de inicio de sesión oficial de 4Geeks; no envíes contraseña ni token por este chat ni los pegues en código. En una configuración nueva, el token debe introducirse en el campo seguro de OpenClaw (bóveda de secretos con entrada enmascarada), autorizando solo el host `breathecode.herokuapp.com`. No se debe guardar como texto en una skill.
- **Configuración encontrada:** la skill existente usa `TOKEN_4GEEKS` desde una variable de entorno; la referencia en la configuración es `${TOKEN_4GEEKS}`. El archivo local de entorno tiene permisos `0600`. La bóveda protegida de OpenClaw figura vacía; se intentó abrir su flujo enmascarado para migrar el token, pero la solicitud falló con `credential-request prompt delivery failed`. No se modificó configuración. La autenticación actual sí pudo probarse con la variable ya configurada, pero no se afirma que el token esté guardado en la bóveda protegida.

## B. Registro individual de skills

### Skill 1 — Autenticación (`authenticate-4geeks`)

- **Prompt en lenguaje natural:** «Skill 1 — Autenticación: Debes poder verificar que mi token de estudiante de 4Geeks es válido y que mi sesión o conexión con la API está activa. Esta skill deberías tenerla ya creada, así que tienes que comprobar que está correcta y funcional».
- **Qué hace:** realiza una comprobación HTTPS de solo lectura; considera token aceptado si `/user/me` devuelve HTTP 200 con JSON, rechazado con 401/403 y no concluyente ante otros errores. Si el JSON incluye una lista `cohorts`, infiere inscripción activa solo cuando alguno de sus `educational_status` es `ACTIVE`. No revela campos de perfil ni nombres/IDs de cohortes.
- **Endpoints reales:** `GET https://breathecode.herokuapp.com/v1/admissions/user/me`, documentado en la referencia oficial de estudiantes. Para la autenticación también se documenta `POST /v1/auth/login`, pero esta prueba no inicia sesión ni envía credenciales.
- **Prueba de funcionamiento:** se ejecutó el helper `skills/authenticate-4geeks/scripts/verify_4geeks_auth.py` usando la variable de entorno ya configurada; además se pasó la validación de skill y la compilación sintáctica de Python. No se invocó la skill a través de una conversación del modelo.
- **Resultado:** el endpoint respondió HTTP 200; el token fue aceptado y la respuesta incluyó una inscripción `ACTIVE`. El helper informó `token_valid=valid` y `active_enrollment=yes`, código de salida 0. `quick_validate.py` indicó `Skill is valid!`; `py_compile` terminó sin error. Resultado verificado para la configuración/variable actual, no para la bóveda protegida de OpenClaw.

### Skill 2 — Proyectos (`4geeks-projects`)

- **Endpoints reales:** `GET /v1/assignment/user/me/task?task_type=PROJECT` con paginación `limit`/`offset`, documentado en la referencia oficial y comprobado en producción.
- **Prueba de funcionamiento:** el helper del grupo `4geeks-student-api` consultó todos los resultados paginados; HTTP 200, `count=40`, 40 filas recibidas.

En los datos reales, los 3 entregados tenían `task_status=DONE`, `revision_status=PENDING` y fecha de entrega, y los 11 aprobados tenían `revision_status=APPROVED`.
